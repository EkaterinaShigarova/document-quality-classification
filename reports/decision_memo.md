# Quality Gate Decision Memo



## 1. Decision

I select **EfficientNet-B0 with a frozen ImageNet base** for the initial CPU prototype. It classifies the whole photograph as good or bad before document type recognition, perspective correction and OCR. This choice follows the acceptance criteria and selection rule recorded in my Task 1 memo. It is a prototype decision based on synthetic images; real-photo testing is still needed.

## 2. Evidence

The full table and figures are in [comparison.md](comparison.md), generated by scripts/collect_results.py from the four results.json files. All runs use the same split, seed 24500007 and 276 test images. The split contains 1,308 training, 216 validation and 276 test images, with all variants of each source kept together.

EfficientNet-B0 achieves **99.28% accuracy**, **0.992753 macro F1** and **98.55% bad recall**. Its measured mean CPU latency is **25.22 ms per image**, below my **100 ms** limit. Its saved float32 checkpoint is **16.31 MB**, below the **50 MB** limit. It has 4,008,829 parameters, with 1,281 trainable parameters in this frozen-base experiment. Training took 60.97 minutes and ran for 50 epochs.

My preregistered rule first requires accuracy at least 0.92, macro F1 at least 0.90, bad recall at least 0.90, latency below 100 ms and saved size at most 50 MB. Among models that pass, F1 differences of at most 0.01 are resolved by lower latency, then smaller size. Both YOLO variants and EfficientNet pass. Their macro F1 values differ by less than 0.01, and EfficientNet has the lowest measured latency.

The trade-off is visible in the confusion matrices. EfficientNet incorrectly accepts two bad images, while each YOLO variant incorrectly accepts one. The accuracy difference between EfficientNet and YOLOv8s-cls is one test image, about 0.36 percentage points. EfficientNet is 6.63 ms faster than YOLOv8n-cls in this benchmark, but a single timing run does not establish a stable speed advantage under every system load.

## 3. Rejected alternatives

**MobileNetV2:** it achieves 99.64% accuracy and 0.996377 macro F1, with one false accept and no false rejects. However, its 135.49 ms latency exceeds the preregistered CPU budget. It is not eligible under the original rule.

**YOLOv8n-cls:** it achieves 99.28% accuracy and 0.992754 macro F1 at 31.85 ms, with a compact 2.96 MB checkpoint. It has one false accept and one false reject. It is a useful fallback, especially if storage becomes the main constraint, but EfficientNet wins the stated latency tie-break in this run.

**YOLOv8s-cls:** it achieves 99.64% accuracy and 0.996377 macro F1 at 89.41 ms, with a 10.26 MB checkpoint. It has one false accept and no false rejects. It is the stronger measured option for reducing unnecessary good-image rejection without adding another bad-image miss, but it is slower than EfficientNet and its F1 improvement is inside the preregistered 0.01 tie range.

These are comparisons of the tested configurations. The YOLO inputs are 640 x 640 with full fine-tuning, while MobileNetV2 and EfficientNet use frozen bases and 224 x 224 inputs. The results do not isolate architecture from input size, framework, head design or training regime. Saved file formats and precision also differ, so file size does not directly measure runtime memory.

## 4. Risks and mitigation

**Synthetic-to-real gap:** the course materials report a 2.8–5.8 percentage-point gap. This is background evidence, not a measured drop for my models. I would test a separate real-photo dataset before using this gate in a real document-processing service.

**Glare:** both EfficientNet errors are INN images with glare predicted good. Across all four models, every false accept is a glare example. I would expand training glare augmentation, check borderline quality labels and include real reflection examples. Any threshold tuning would use validation data, not the reported test images. A production pipeline should allow operator verification and record difficult cases for later review.

**Small test set:** one error changes accuracy by about 0.36 percentage points. The current numbers cannot show a statistically reliable winner on real documents. More independent source documents and repeated timing measurements would make the decision more reliable.

**Gallery shortfall:** the assignment asks for five errors per model, but these test runs produced fewer. All actual errors are listed in [error_analysis.md](error_analysis.md). This numerical requirement remains unresolved and needs an instructor decision.

## 5. Deployment note

For a CPU server prototype, I would load the saved EfficientNet weights once, recreate the binary head and use evaluation mode. Input processing must match training: RGB, full-image resize to 224 x 224, pixel scaling to [0, 1], then ImageNet mean [0.485, 0.456, 0.406] and standard deviation [0.229, 0.224, 0.225]. The sigmoid decision threshold remains 0.5. Bad predictions should trigger a request for a new photograph before later processing stages.

The recorded 25.22 ms latency includes preprocessing and prediction after image decoding. It does not include model loading, file decoding, Telegram communication or the later OCR stages, so it is not the full bot response time.

For mobile or edge deployment later, I would first investigate ONNX export and check prediction agreement on the same images. Latency, memory and file size must then be measured on the actual target device. A TFLite route would require a compatible conversion workflow and the same agreement checks. No export or mobile benchmark has been completed in this work.
